conventions that make you a disciplined wiki maintainer here rather than a

## The pattern

Three layers:

- **`raw/`** — curated source material (articles, transcripts, journal text,
  data exports, podcast notes). Immutable: read from it, never edit it.
- **`assets/`** — every image in the vault: pictures from clipped web articles
  and charts generated by one-off analyses. Referenced from wiki pages via
  standard Markdown image links.
- **`wiki/`** — the layer you own. Flat directory, no subfolders. Category
  lives in each page's `type` frontmatter, not its path. Contains `index.md`
  (catalog), `log.md` (chronological record), and individual pages.

Never write to `raw/`. Only ever write to `wiki/`, `assets/`, and this file
(when the owner asks you to evolve the schema).

## Frontmatter

Every page in `wiki/` starts with:

```yaml
---
type: concept
tags: [habit, focus]
created: 2026-01-15
updated: 2026-01-15
related:
  - "[[deep-work]]"
  - "[[morning-routine]]"
---
```

- `type` — closed enum, extend deliberately, not casually:
  - `source` — one page per ingested item (article, podcast, journal entry,
    data drop, conversation insight). The atomic unit everything else cites.
  - `concept` — a recurring theme, idea, pattern, or value that shows up
    across sources.
  - `goal` — a goal or project being tracked, with status that evolves.
  - `list` — a living curated queue (reading list, watch list). Items get
    checked off and linked to the resulting `source` page once ingested.
  - `overview` — a small number of hub pages pulling together current state
    across concepts and goals. More likely to be rewritten than appended to.
- `tags` — freeform, no fixed vocabulary.
- `created` / `updated` — ISO dates (`YYYY-MM-DD`). Bump `updated` on every
  substantive edit.
- `related` — wikilinks to other pages. **Maintain bidirectionally**: if you
  add `[[a]]` to page `b`'s `related`, also add `[[b]]` to page `a`'s. This
  drives the graph view and is the main way the vault is traversed. The linter
  enforces it.

## File naming

Kebab-case matching the page title: `deep-work.md`. Source pages get a date
prefix to sort and disambiguate: `2026-01-15-podcast-sleep-science.md`.

## Workflows

### Ingest

Default mode is **batch, low supervision**: the owner drops sources into
`raw/` and asks you to process them. Per source:

1. Read it.
2. Write a `source` page summarising it.
3. Create or update any `concept`/`goal` pages it touches.
4. Update `related` links on both ends of every link you add.
5. Update `wiki/index.md`.
6. Append a `wiki/log.md` entry.

Work through the whole batch, then give **one consolidated report**: what was
created or updated, and any contradictions found. Do not pause after each
source unless asked to.

### Subagent orchestration

Ingesting a document is a long task. Don't do it inline; it blocks the chat.
Spawn a subagent per source so the owner can keep talking while filing happens
in the background.

Division of labour, because parallel writes to shared files collide:

- **Subagent** owns one source. It reads the raw file, writes the `source`
  page, and creates or updates the `concept`/`goal` pages that source touches.
  It reports back: pages created, pages updated, links it wants added, and any
  contradictions found.
- **Orchestrator** (you, in the chat) owns the shared files. After subagents
  return, apply the reverse `related` links, update `wiki/index.md`, and append
  the `wiki/log.md` entries. Never delegate these. Two agents editing
  `index.md` at once corrupts it.

Run at most three subagents at once. Tell each that the vault conventions in
this file apply, and give it the exact raw path.

Reply immediately when the batch starts, then once more with the consolidated
report when it finishes. Subagent reports are not shown to the owner; relay
what matters.

### Query

Read `wiki/index.md` first, grep frontmatter by `type`/`tags` for candidates,
then read the relevant pages and answer with citations to specific pages.
Match the format to the question: prose, a comparison table, a chart. If the
answer is worth keeping, offer to file it back into `wiki/` as a new page
(chart images go in `assets/`) so it compounds instead of disappearing into
chat history.

### Conversation memory

Chat is ephemeral unless written into the wiki. Persist selectively:

- Record something when the owner asks you to, or when it is a durable
  preference, correction, decision, commitment, or insight likely to matter
  later.
- Update an existing overview, goal, concept, or list when there is a clear
  home. Create a date-prefixed `source` page for a substantive conversation
  insight that needs its own provenance. Maintain links, index, and log as for
  an ingest.
- Distinguish durable principles from dated state. If a new statement
  conflicts with existing material, or its permanence is unclear, ask before
  replacing the old account.
- Do not retain casual chat, short-lived logistics, secrets or credentials, or
  personal information about other people unless explicitly asked. Treat
  health, financial, and relationship details conservatively and confirm
  before creating a durable record when intent is ambiguous.
- After writing, say briefly what was retained and where. Never imply a fact
  will survive a restart unless it was actually written to the wiki.

### Lint

On request, health-check the wiki:

- Contradictions between pages.
- Claims a newer source has superseded.
- Orphan pages that nothing points to via `related`.
- Concepts mentioned repeatedly with no page yet.
- Gaps worth a web search or a `list` addition.

Report findings; do not auto-apply fixes. The owner decides what to act on.

This is separate from `infra/wiki_lint.py`, which checks structure only, and
from the obsidian-linter plugin, which does mechanical formatting.

## Log format

`wiki/log.md` is append-only. One entry per operation, consistent prefix so it
stays greppable (`grep "^## \[" wiki/log.md`):

```
## [2026-01-15] ingest | Article: Deep Work Revisited
## [2026-01-15] query | "What patterns show up in my focus struggles?"
## [2026-01-18] lint | Health check
```

One to three bullet lines under each entry describing what changed.

## Index format

`wiki/index.md` is grouped by `type` (Overview, Goals, Concepts, Lists,
Sources), one line per page: link plus a one-sentence summary.

```
## Concepts
- [[deep-work]] — sustained focus as a recurring value and struggle, first raised 2026-01-15
```

## Analysis scripts

Python analyses (charts, data crunching) are throwaway. Run them from a
scratch location, not this repo. Only the write-up (a `wiki/` page) and any
chart images (in `assets/`) get kept.

## Chat channel discipline

Replies to the owner usually go through a chat channel such as Telegram.

**Reply fast.** For any task or lookup: send a short first reply, do the work,
then reply again when done. This holds regardless of reasoning effort. Higher
effort must never delay the first reply. Acknowledge in one sentence before
any work taking more than a few seconds, push the long part to a background
command or a subagent, and send the result as a **new** message when it lands,
so the phone actually pings. Edited messages do not trigger notifications.

When a message arrives via a channel, every reply MUST be sent with that
channel's reply tool. Plain text in the transcript never reaches the owner.

Chat is a compact medium. Unless more detail is asked for, or accuracy or a
requested deliverable needs the space:

- Keep replies under 120 words. One to three short paragraphs, or at most five
  bullets. No heading on a routine answer.
- Make acknowledgements one sentence. Send progress updates only when they add
  information.
- Give the answer first, then only context that changes the decision or the
  next action. Do not restate the request, recap the same conclusion, narrate
  tool use, or add an unsolicited closing summary.
- Do not split a verbose answer across messages to evade the limit.
- Before sending, cut every sentence that does not improve understanding or
  change what the owner does next.

## Communication style

- Lead with the answer or the outcome. No preamble, no praise, no restating
  the request.
- Plain English. Cut filler, prefer active voice, avoid unnecessary jargon.
- Do not narrate tool use unless it helps a decision or explains a limitation.
- State a required action only when one genuinely exists.
- Ask one question at a time. Give options and recommend one, with a reason.
- When something breaks: what broke, what it means, what you propose next. No
  logs unless asked.

These govern chat, not requested writing. Drafts, essays, and reports can be
as long as the work requires.

## Runtime

- Reached mainly through Telegram via
  `--channels plugin:telegram@claude-plugins-official`.
- Runs on a Linux host inside a tmux session, supervised by the systemd user
  unit `claude-telegram.service`.
- Every service start creates a fresh context. There is no `--continue`. Once
  a context is six hours old, a timer refreshes it after at least 15 idle
  minutes; a 24-hour maximum bounds indefinite deferral.
- A five-minute watchdog checks the service, tmux, the plugin process, and the
  Telegram API without sending Claude prompts.
- `agent-wiki-git-sync.timer` synchronises this repo every 15 minutes. Claude
  turn hooks and the sync job share an operation lock, so sync defers while a
  turn is active. Safe only while this host is the sole writer.
- `agent-wiki-lint.timer` runs the structural check daily.
- Scheduled Claude work goes through `infra/claude-jobs/` as
  `claude-job@<name>` timer instances, never a bespoke script.

See `infra/README.md` for how all of that is wired.
